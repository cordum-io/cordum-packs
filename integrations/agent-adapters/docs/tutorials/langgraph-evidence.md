## What the live tests establish

1. **Allow:** a native LangChain tool generated by `build_langchain_tools` runs inside a real LangGraph node, crosses MCP stdio and the actual Cordum job pipeline, and produces the transform output `{"greeting":"Hello langgraph"}`.
2. **Deny:** the actual default-deny policy selects `langgraph-demo-deny-cancel`. Core persists `DENIED` and a synthetic denial result. The actual Redis transition history contains no `SCHEDULED`, `DISPATCHED`, `RUNNING`, or `SUCCEEDED`; attempts remain zero. This is evidence of no tool dispatch, rather than merely checking a denial string.
3. **Approval:** the graph checkpoints the existing job and interrupts. Resuming alone leaves it pending. The requester key receives HTTP 403 on self-approval. A separate temporary operator key approves it; the original job executes and succeeds. A spy wrapping the real MCP client confirms exactly one `tools/call` submission.
4. **Changed resume input:** after the original job is approved, edited resume arguments are rejected by the application. The stored original job succeeds, and no second tool submission occurs. This is not a server approval-token guarantee.

## Bounded repairs and limits

- The integration collection hook previously skipped every adapter test when the integration flag was absent. It now skips only the integration directory; six regression cases cover that boundary.
- CAP 2.17 rejects the bridge's unconfigured signing path. An explicit, default-off unsigned compatibility option now permits disposable development only: development environment, compatibility profile, loopback endpoints, and no production override. Gateway redirects are refused in that mode. Full signing-key/production admission configuration remains unsupported by this bridge.
- Submit-time policy HTTP 403 previously became MCP JSON `null`. The bridge now recovers the referenced stored job only when the lookup confirms the same ID in `DENIED`. Auth errors and unverifiable denials retain the original failure.
- The packs bridge returns approval-required metadata and the original job ID. It does not provide the separate Core MCP `_approval_ref` replay protocol. Resume observes that job; it does not invoke the tool again.
- The input digest is an application check within trusted checkpoints. The approved original may already execute before an edited resume is rejected. The check does not undo that action or protect against an attacker rewriting the entire checkpoint.
- Checkpoints are in memory; process-restart recovery and exactly-once external effects are not claimed.
- The fixture uses authenticated plaintext only on loopback. Production TLS and authentication defaults are untouched. The bridge's HTTPS client uses system trust and does not consume `CORDUM_TLS_CA`; the Python observer's `--ca-file` does not change that.
- The rerun demonstration supplies `from_step='echo'`, as required by the tested current Core workflow route.
